# OrgForge 0.14.0

OrgForge now carries work from sign-off into production, keeps working when an
engine hits its usage limit, and learns from what actually happened to the work
it reviewed.

- Engine failover: a limited engine rests until its reported reset time and the
  assignment continues on the next ready model; the project pauses only when
  every option is resting. API rate limits and unreachable local model servers
  count as limits.
- Codex tested against Codex CLI 0.160.1 on a ChatGPT plan with a full task.
  Fixed builder permissions (`--full-auto` was removed), stdin prompts, limit
  detection after Codex's echoed prompt, and token totals.
- Production stage: signed-off releases deploy environment by environment with
  health checks, optional CEO/CTO go-aheads, automatic rollback to the last
  healthy version, incident tickets, and optional ongoing health monitoring.
  Deploy commands are set by people in `org.yaml`, never by agents, and receive
  only the secrets listed for them.
- The learning loop runs itself: review verdicts are settled by escalation
  rulings, release checks and accepted releases, and score reviewers and QA;
  repeated failures across tickets produce a strategy proposal that competes
  with the current approach once the CTO approves it.

Existing companies receive additive database migrations. Failover and production
deployment are opt-in. Learning and routing are on for new companies and change
nothing without evidence or routing rules; companies whose `org.yaml` sets them
to `false` stay off. Back up company data before upgrading.

Gemini CLI and the other built-in CLI engines besides Claude Code and Codex are
still untested. Real usage-limit messages were simulated, not triggered. The
production stage was exercised with local deploy commands, not a cloud provider.

Validation includes 229 offline tests, a real Codex task (build, code review,
QA, checks), and dashboard walkthroughs of failover, deployment approval and
the learning loop.
